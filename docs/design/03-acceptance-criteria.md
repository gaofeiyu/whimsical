# 03 - Editor Engine Acceptance Criteria (验收标准)

为了确保我们的低代码引擎在接入 AI Chatbot 或进行代码双向还原之前，具备真实可用的页面搭建能力，我们需要一套客观的验收标准。
本标准以**“能够100%还原一个典型现代响应式网站（如 SaaS 产品落地页或管理后台看板）”**为目标。

如果以下清单未被全部满足，则说明当前的 DSL、排版机制或交互引擎仍有缺陷，不应过早进入下一阶段（AI 接入）。

---

## 1. 核心布局能力 (Layout & Structure)

在真实网页中，布局是骨架。引擎必须能表达复杂的 CSS 盒模型和定位：
- [ ] **多级嵌套容器**：能够实现深层级的容器嵌套（如 Page > Section > FlexBox > Card > Button）。
- [ ] **流式与弹性布局 (Flexbox)**：
  - 支持配置主轴/交叉轴对齐方式（`justify-content`, `align-items`）。
  - 支持配置方向（`flex-direction`: row / column）。
  - 支持换行（`flex-wrap`）和元素占比（`flex: 1`）。
- [ ] **间距与尺寸 (Spacing & Sizing)**：
  - 支持直观设置内外边距 (`padding`, `margin`)。
  - 支持宽度、高度（包括百分比 `%`, `px`, `vh/vw`, `auto`）。
- [ ] **定位 (Positioning)**：
  - 支持相对定位 (`relative`) 与绝对定位 (`absolute`)。
  - 对于绝对定位元素，支持配置 `top, right, bottom, left` 及 `z-index`。

## 2. 基础组件与属性控制 (Components & Props)

除了布局，还需要有能够承载内容的原子组件，并支持复杂的属性配置：
- [ ] **动态组件库接入体系**：
  - 必须提供一个组件封装和注册体系，低代码引擎不应与具体的 UI 库（如 Ant Design 或 MUI）强耦合。
  - 能够根据需要动态加载组件并使得引擎“认识”这些组件的渲染方式。
- [ ] **自适应属性配置面板 (Property Panel)**：
  - 必须提供一个可视化的配置面板，能够根据当前选中组件的 Schema 动态生成对应的配置表单，以适应网页能力的变化。
- [ ] **原子组件库**：至少提供排版所需的 `Text`, `Image`, `Button`, `Divider`, `Input`。
- [ ] **样式透传 (Style Binding)**：
  - 能够实时调节字体（大小、颜色、行高、粗细）。
  - 能够调节背景（背景色、背景图）、边框（宽度、颜色、圆角 `border-radius`）和阴影 (`box-shadow`)。
- [ ] **交互与状态伪类**：
  - 支持定义 `hover`, `active` 状态下的样式变化。
  - *(加分项)* 支持响应式断点（在 Mobile / Desktop 下呈现不同的样式）。

## 3. 编辑器交互体验 (Editor UX & Precision)

编辑器的操作必须符合人类的直觉，这是保证生成的代码可读、可维护的前提：
- [ ] **精确的拖拽碰撞检测 (Drop Indicator)**：
  - 当拖拽组件时，能够精准识别是插入在目标元素的**前面、后面、还是内部**。
  - 在画布上有明确的高亮指示线或占位符，所见即所得。
- [ ] **选中与层级导航 (Selection & Breadcrumbs)**：
  - 点击画布上的元素能够精确选中目标。
  - 考虑到多层嵌套，必须提供一种方式（如底部面包屑或左侧大纲树）让用户选中被遮挡的父级容器。
- [ ] **撤销与重做 (Undo / Redo)**：
  - 任何针对 DSL 的修改（拖拽插入、属性变更、删除）都必须可回退。
- [ ] **组件拖动排序 (Move/Reorder)**：
  - 支持将画布上已有的组件进行二次拖拽，重排到画布的另一个位置（避免必须删除再重新拖拽的糟糕体验）。

## 4. 双向代码还原机制 (Code Reversibility Engine)

我们的最终目标是支持代码的双向绑定，即“DSL -> 源码 -> 用户二次开发 -> 源码反向解析回 DSL”，因此引擎必须具备以下机制：
- [ ] **模式切换能力 (Mode Toggling)**：
  - 画布上方必须有一个明确的模式切换按钮，支持在“DSL 渲染模式”和“真实代码模式 (Code Mode)”之间无缝切换，用于实时识别和验证双向还原体系是否有效。
- [ ] **明确的双向还原架构设计**：
  - 必须有前置的架构文档清晰说明 AST 解析、增量比对策略以及标记机制。
- [ ] **确定性的 ID 注入**：渲染出的每一层真实 DOM / React Component，都必须带有唯一的 `data-w-id` 或类似的标记。
- [ ] **框架无关的干净 DSL**：`NodeTree.serialize()` 导出的 JSON 不能包含不可序列化的对象（如函数、React Context），它必须是一份纯净的 JSON 配置树。
- [ ] **无损反序列化**：引擎必须能够通过读取一份导出的 JSON DSL，百分之百还原出原有的画布状态（`loadFromData`）。

### 验收流程 (基准页面)

在进行下一步（如 AI Chatbot 接入）之前，开发者必须尝试使用当前编辑器纯手工（或通过编写脚本调用 `executeCommand`）复刻 **[Vite 官方主页 (https://vite.dev/)](https://vite.dev/)**。

我们将以该页面的以下几个结构为核心验收目标：
1. **顶部导航栏**：横向弹性布局，包含 "Guide", "Config", "Plugins" 等文本或按钮。
2. **Hero Section**：包含主标题 ("The Unified Toolchain for the Web" 等)、渐变文字和主操作按钮。
3. **特性列表 (Features Grid)**：如下方的卡片阵列，用于验证栅格或多行多列的 Flex 布局。

只有当该页面能够被完美渲染、视觉上与原页面高度相似，并且导出的 DSL 依然干净纯粹能够被 100% 重新反序列化时，才标志着当前基础搭建引擎重构阶段真正验收通过。
