# 04 - 核心架构实施阶段计划

考虑到验收标准（见 `03-acceptance-criteria.md`）中对低代码引擎的要求极高（尤其是与组件库解耦、双向代码还原、以及画布内的二次拖拽等高级用户体验特性），试图在一个阶段内完成所有特性是极度危险且不可控的。

为了确保每一步的基石都坚实可靠，我们采用**渐进式验证**策略，将整体目标的实现拆分为以下四个独立交付且可独立验收的阶段：

## 阶段一：动态组件注册与自适应配置面板（桥接层）

在这个阶段，我们将打破目前硬编码的假组件，建立起“引擎”与“第三方组件库”之间的桥梁。

- **核心任务**：
  1. 设计并实现组件注册中心：允许外部传入组件配置（包含组件的渲染函数、接受的属性定义、默认样式等），从而让引擎“认识”这些组件，而不是与特定 UI 库拟合。
  2. 实现动态属性面板：右侧的设置面板不再是写死的结构，而是根据当前选中节点在注册中心中的结构定义，动态渲染出对应的配置表单（如颜色选择器、文本框等）。
- **验收目标**：成功注册一个外部按钮和容器，点击它们时，右侧能动态生成正确的属性修改面板。

## 阶段二：画布高级交互与精准排版（用户体验层）

在此阶段，我们将完善用户的物理拖拽体验，这是实现极其复杂的 Flexbox 嵌套布局的前提。

- **核心任务**：
  1. **支持二次拖拽 (Move/Reorder)**：修改现有的 `onDragStart` 和 `onDrop` 逻辑，允许用户抓起画布上已经存在的节点，并触发 `executeCommand('move', targetId, payload)`。
  2. 完善占位符与碰撞检测：确保嵌套深处的容器能够正确响应拖拽事件（避免事件冒泡带来的父子容器判定冲突）。
- **验收目标**：用户能够纯靠鼠标，在画布内将一个存在的组件从容器 A 流畅地拖拽移动到容器 B，或在兄弟节点间交换顺序。

## 阶段三：双向代码转换架构与模式切换（编译引擎层）

这是整个系统中最具挑战性的一环。我们将实现“模式切换”，真正打通 DSL 与代码的双向壁垒。

- **核心任务**：
  1. 出具专门的双向还原架构设计文档（明确基于抽象语法树或特定标记的解析策略）。
  2. 实现 DSL 渲染模式与真实代码模式的视图切换按钮。
  3. 实现从 DSL 实时生成带特定标记的 React 源代码。
  4. 实现从修改后的 React 源码中，依靠特定标记和语法树解析工具重新逆向解析并更新回响应式状态树。
- **验收目标**：用户在画布上拖出一个按钮，点击切换到“代码模式”，修改代码里的按钮文案，再切回“DSL 模式”时，画布上的按钮文案同步更新且结构不乱。

## 阶段四：基准里程碑验证

所有子引擎和能力准备就绪后，我们将执行最终的集成测试。

- **核心任务**：
  1. 使用上述完成的能力，全量复刻 **Vite 官方主页**。
  2. 验收所有布局细节（导航栏、核心展示区、特性卡片阵列）。
- **验收目标**：完美渲染目标页面，且导出的 DSL 依旧保持纯粹和百分之百可复原。

---

**只有当阶段一到阶段四均通过验收后，我们才会正式进入最终的 AI Chatbot 接入阶段。** 因为只有当手动拖拽和底层机制绝对可靠时，AI 生成的指令才能被准确无误地执行和呈现。
